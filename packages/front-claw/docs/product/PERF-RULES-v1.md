# Front Claw 业绩口径规则 v1.1（2026-11-12）

本规则参考了门店常用的第三方美业系统的业绩口径，但只取其中一个子集，并按产品需要做了简化。第三方系统的取证材料不在本仓库。

## 1. 关键事实：业绩不是单一的一个数
美业系统里的业绩通常分几类：开单人业绩、共创人业绩、耗卡业绩和门店业绩。Front Claw MVP 只做其中的开单业绩，并保证业绩类型以后可以扩展。

## 2. MVP 规则
R1. **员工私聊报的单，记为「开单业绩」**。括号里写的员工就是开单人；没写括号的，开单人是报单人本人（D81）。
R2. **只有已确认的单才计入业绩**。员工回「对」之后才算确认；待确认的单不计入任何统计。
R3. **门店业绩 = 本店当天或当月已确认开单业绩的合计**。这是**产品简化**。以后如果要把一单拆到几家门店，改成「基数 × 门店比例 / 100」，各店比例合计 100%。
R4. **月目标完成率 = 当月已确认的开单业绩 ÷ 门店月目标 × 100%**，保留两位小数。**不封顶**，超额就显示超过 100%，让店里看得到超额。
R5. **共创人、耗卡、多人分配比例 MVP 不做**，以后用 entry_credits 子表扩展，业绩类型要能扩展，不写死成只有 consultant。以后做分配时遵守这些约束：
  - 员工金额 = 同一个订单基数 × 员工比例 / 100，不是在门店金额上再乘一次；
  - 员工比例要大于 0，且不能超过所在门店的比例（容差 0.01），这就是「门店上限」；
  - 门店之间的比例合计必须是 100%，员工之间不要求加起来等于 100%。
R8. **业绩基数是折后成交额**，也就是员工实际收到的钱。
  - 员工报数时直接报折后的实收金额，系统不再扣一次折扣；
  - 赠送金额不计入，比如充 1000 送 200，只记 1000；
  - 充值实付计入开单业绩。MVP 不单独做充值类型，员工按实收报就行。
  - 外带单以后如果要做，业绩按总价格、收款按实收，分开记。
R6. **提成、手工费不算业绩**，MVP 也不做。
R7. **退款**：MVP 不处理退款，金额有误一律走改单，改单要留下原值和新值。以后如果做冲减，原业绩和净业绩分两组存，不在同一个字段上覆盖。

## 3. 金额规则（按 hanyu 要求定）
A1. **金额精确到 0.01**。原来的 D80"只收整数元"作废。「680.5元」可以直接收；超过两位小数的才追问。
A2. **取消单笔金额上限**，也不做大额二次确认，所以 D84 的 100 万上限和 5 万多确认一次都撤掉。技术上只保留数据库字段能存下的上界，用来防溢出，不算业务规则。
A3. **金额为负或为 0 的追问**。
A4. **模糊金额照常追问**，比如「六百多」「大概 680」，D82 不变。
A5. **展示单位**：员工说的是元、块，回显用「元」。

## 6. 和架构负责人对齐后的修订（12:19）
- 不加 allocation 和 refund_flag。等以后做共创人时，再单开一张子表 entry_credits(entry_id, person_id, perf_type, share)。perf_type 直接用现有的 amount_type 列，值填 consultant。
- 金额列改成 numeric(14,2)，计算全程用定点数，不经过 JS 浮点。
- **门店月目标单独建一张表**，比如 store_targets(store_id, period_month, amount, set_by)。不用约定的特殊 person_id 来表示整店，免得统计时被误算成一个员工。R4 的完成率默认用门店月目标来算；个人目标表保持现状，店长愿意设就设，不设也不影响门店完成率。
- status 加 CHECK 约束，只允许 pending、confirmed、voided 三个值。
