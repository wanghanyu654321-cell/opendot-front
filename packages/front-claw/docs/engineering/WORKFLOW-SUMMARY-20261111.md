## 一句话主线

> 用大模型写代码，最怕的不是模型不够聪明，而是人没有把**问题和边界**定义清楚。一个大 Goal Prompt 会换来“单测全绿、真实链路断裂”。所以要把需求拆成**带基线、范围、非目标、验收命令的 Issue + Plan**，交给本地 Codex 一小片一小片做，人类只做**边界把控和审查**。

## 0. 根页面：总纲

**两件事**：① 一套能落地的开发工作流；② 项目的真实演进历程（痛点、弯路、审查中发现的隐患、工程沉淀）。

**三阶段工作流**（原文有 mermaid 流程图）：
1. **网页端聊方案（WebSearch + 方案设计）**：痛点 → 联网大模型调研开源方案和选型 → 定边界 → 沉淀成两份本地文件：**Issue**（做什么、不做什么）和 **Plan**（改哪些文件、步骤、验收命令）。
   - 为什么在网页端做：可以联网查最新文档、已知缺陷和最佳实践；先想清楚架构、接口和数据结构；输出放进仓库的标准 Markdown。
2. **本地 Codex 执行**：认领 Issue → 读 Plan 和本地代码上下文 → 分步写代码、补测试 → 在本地或容器里跑通测试。优势是目标单一、能感知本地上下文、用测试驱动交付。
3. **人工审查与合并**：看 Git Diff，检查有没有超出范围、测试是不是真实环境跑的、有没有用假数据。发现问题就把报错和复现步骤写回 Issue。

## 1 story（故事线，4 篇；目录页本身只有链接）

### 1.1 01｜故事起点：从桌面个人助手出发
- **痛点**：自用的桌面助手绑死在笔记本上。合上屏幕，后台任务就中断；在外面用手机连不上。
- **目标**：升级为 Personal Agent。离开电脑也能用手机查看和追问；长任务在后台持久运行；以后支持多个智能体协作。
- **原则：不从零手写**。旧系统已有执行引擎、桌面外壳、用户认证、工作区管理和权限调度。重写既浪费时间又会让稳定功能退化。要做的是理清“哪些直接复用、哪些增量接入”。
- **技术分层**：① 跨设备随身访问（注意：网络连通 ≠ 关机后任务还能继续）；② 长任务离线持久化（生命周期、崩溃和关机后的恢复）；③ 产品外壳与权限层（复用界面、模型配置、人工审批）。
- **两步走**：先做随身查看（PR #002，复用前端外壳和后端认证），再研究云端离线恢复（PR #020）。
- **体会**：先把想法拆成具体的产品能力，再用最小改动接进现有系统，永远不要冲动地推倒重来。

### 1.2 02｜从大提示词到 Issue 驱动
- **失败经历**：写了一份几千字的 Goal Prompt，让 Agent 自己读代码、拆阶段，独立完成持久化、多设备接续、主动任务和长记忆，再补齐单测和故障模拟。
- **结果**（提交 `fe520f58`）：单测全部 PASS，但业务没有串起来。沙箱里验证了“中断能恢复”，前端也加了按钮，可用户创建的真实任务仍然走老的本地临时调度器，没接入新的持久化机制。
- **根因**：目标太大、跨的边界太多，AI 遇到不确定的地方就会“**局部打桩**”，用模拟数据让自己的测试通过。
- **转折**：“你提 Issue 就好了，Issue 里写明相关实现计划，最好是方便本地直接认领开发。”
  - 网页端：联网检索，明确“做什么 / 坚决不做什么”，输出 Issue（目标、现状、验收标准）和 Plan（切片步骤、涉及文件、测试命令）。
  - 本地 Codex：单点认领，按计划改动，每一步都跑真实测试。
- **第一次见效**：Issue #30 总路线图，加上 #31~#35 五个切片（首页入口、群聊数据模型、定向交接、云端适配、产品验收）。每张 Issue 都写明参考提交、改动文件、测试命令和非目标。之后 AI 不再发散，审查的范围也可控了。

### 1.3 03｜群聊是怎样迭代的
- **产品原则**：Conversation-first（对话视口和输入框是主角，复杂配置收进抽屉，见 #61）；**Dot** 是最小智能体单元，有独立身份、会话存储和工具权限。
- **群聊初版的尴尬**：多个 Dot“接力写作文”，B 先复述 A 的话再说两句套话，然后交给 C。于是立了 Issue #69，PR #070 交付了基础讨论服务。
- **源码复核的反转**：一开始怀疑消息传递坏了。实际上持久会话和公开时间线早就通了，问题出在 Prompt 规定“发言前必须按序号总结上一位”。
- **Issue #71 纠偏**：① 废除复述规训，直接发表增量观点、补充或反驳；② 支持主动 **Pass**，讨论收敛时不硬凑。
- **做减法 #75–#78**：#75 界面去噪（隐藏调度日志和调试时间戳，只留审批卡片和最终文本；**坚决不做流式打字展示**，避免卡顿和状态错乱）；#76 策略默认值安全，保护历史会话；#77 每个 Dot 一个独立 Inbox，异步流转；#78 有界并发，保证单 Session 执行流稳定。
- **体会**：把“明确不做的事”写清楚，和把“要做什么”写清楚一样重要。

### 1.4 04｜多分支集成与审查排雷
- **后期四个并行方向**：MCP 外部工具（#103）、电脑桌面操作（截屏 + 受控键鼠，#101）、Mem0 长期向量记忆（#110）、Langfuse 全链路观测（Token、调用链，#111）。
- **现象**：每个分支单独跑都是绿的，合进集成分支后问题全暴露了。
- **审查拦下的三个隐患**：
  1. **PR #109 假单测**：用了极简 Mock 夹具，绕过了生产默认必须走的 Docker 容器隔离。打回，要求在真实容器里补齐挂载和权限验证。
  2. **PR #116 记忆越权提权**：把 Mem0 检索出的记忆拼进了 `system` 根指令。一旦记忆里混入 Prompt Injection，就拿到了最高权限。打回，降级放进受限的 `user` 上下文知识字段。
  3. **PR #115 幽灵 Trace 丢失**：Mem0 在后台做摘要压缩时，拦截器静默截断了请求头里的 Trace Context。重构中间件，保证 Trace 标识无损透传。
- **代码同步 ≠ 发布**：PR #149 把集成分支合回 `main`，但合并说明里写明这只是阶段性基线同步，不代表全部达到生产标准。要坦诚写出“已验证 / 测试中 / 受环境限制未覆盖”。

## 2 workflow（标准工作流 SOP，4 篇）

### 2.1 需求如何写成 Issue
目标：接手的 Agent 不靠猜就能开工，同时实现细节留给它。Issue 要融合用户诉求、现有代码和交付边界，不能只是贴聊天记录。
1. **把痛点转成可观察的结果**：不写“优化群聊”，而写“用户建群、选多个 Dot、提问后，后续 Dot 能读取前面的真实发言并增量讨论”（#69）。同时记下当前行为（已有 `@Dot` 和手动 Handoff），避免重复实现已有能力。
2. **先核对本地代码库**：写明分支和基线提交，读入口、数据结构和测试。（#71 就是复核后发现能力已有，修正了先前的判断。）推荐分三栏：**已确认的现状**（有代码、单测或 PR 为证）/ **推断或未验证**（需要实验确认）/ **本 Issue 新增工作**。旧提交只用于追溯，开发前要检查最新分支。
3. **拆成能独立交付的切片**（#30 拆成入口、数据模型、Handoff、生命周期、验收；#75–#78 再细分），回答 5 个问题：先决依赖、并行边界（共享数据契约谁负责）、独立验证（PR 的物理边界）、向下兼容（运行中的会话、旧客户端）、明确排除（Non-Goals，例如不做流式打字）。
4. **写清“完成”的证据**：正常路径和失败防御路径都要有。群聊要查身份隔离、上下文互读、防重复提交、主动打断、权限和 Token 预算；设备操作要注意“工具出现在配置里 ≠ 模型真能在容器里安全操作”；验收记录写提交、环境（本地或 Docker）、命令和结果。
- **自检**：Issue 能否独立回答 **为什么做、从哪儿开始、哪些不能动、怎么拆、什么证据证明完成**。然后交给本地 Codex。

### 2.2 网页端聊方案与本地 Codex 认领执行指南
- **为什么分开**：改小函数可以在 IDE 里直接让 AI 做；涉及架构选型、接口重构或多模块联动时容易失控。网页端能实时检索（本地 Agent 受训练截止时间和上下文限制），先想清边界，再输出标准文档。
- **第一阶段（你是产品经理加架构师）**：提痛点和目标 → 让 AI 联网搜社区做法并对比 → 告诉它现有核心数据结构和接口，要求做增量扩展、不发明不兼容的新轮子 → 生成两份文件：`docs/issues/issue-xxx.md`（背景、现状、交付物、验收、非目标）和 `docs/plans/plan-xxx.md`（切片顺序、文件、改动要点、测试命令）。
- **第二阶段：派给本地 Codex 的结构化指令模板**：
  ```
  请认领并执行以下任务：
  1. 任务说明：阅读并遵循 Issue #69 契约文档
  2. 实施计划：阅读配套 Plan，按顺序推进
  3. 代码核对：先检查当前分支和现有测试，确认与计划假设一致
  4. 约束边界：仅实现增量逻辑，不破坏已有会话管道
  5. 交付证据：每完成一个切片，在本地终端跑测试，确保用例真实跑通
  ```
  执行规范：先读后写（确认假设没过时）、小步切片（不做散弹式改动）、补齐真实测试（严禁用 Mock 绕过核心逻辑）。
- **第三阶段（人工审查）**：查 Diff 范围 → 甄别假测试（PR #109）→ 把关安全（记忆不能提权成 system，PR #116）→ 合并，或把错误写回 Issue。

### 2.3 怎样审查 PR 并把问题回写
- **先确定审查对象**：目标分支、head SHA、关联 Issue、依赖和已有验证证据。分支名或标题不能证明改动范围，堆叠 PR 的祖先可能带着大量其他提交，必须看实际 Diff。PR #109 的例子：固定基线，同时检查与 #101/#103/#110/#111 的兼容性，发现默认 Docker 路径与群聊运行条件不匹配，Host-only 夹具通过不能代表容器通过。
- **四个维度**：① 真实产品路径（入口能否走通、失败时有没有提示和降级）；② 既有系统边界（身份隔离、授权、持久会话、旧数据兼容）；③ 并发与异常（重复点击、网络瞬断、重启、打断、工具超时）；④ 证据与结论是否匹配（Mock、本地仿真，还是真实容器）。不重复提已经关闭的问题，也不把未证实的风险夸大成故障。
- **有效反馈四要素**：触发条件、实际行为与风险、期望边界（数据契约和权限级别）、可验证的命令或用例。实例：#116 要求降权到 `user` 字段，并补 Prompt Injection 防御用例；#115 要求补“ProductRuntime 真实链路 + 记忆注入 + 观测收集”的端到端用例。
- **写回位置**：只影响单个 PR 的问题写在 PR 评论里；影响下游契约的，还要在 Issue 文件里追加说明。
- **分批准入**：闭环且测试充分的先进集成分支；边界存疑、测试不严或权限越界的暂缓。

### 2.4 怎样测试、集成与合并
- **“通过”的范围表**：
  | 证据 | 能证明 | 不能自动证明 |
  |-|-|-|
  | 类型检查 / 构建 / 单测 | 该提交在特定环境下满足断言 | 端到端链路、真实多模型协作、线上部署 |
  | 集成测试 / 模拟 Provider | 模块间接口契约和基础异常处理 | 真实计费、设备权限、长连接抖动 |
  | 浏览器 / 手机视口自动化 | UI 元素、表单、响应式 | 原生权限弹窗、系统级快捷键 |
  | 真实模型与物理设备实测 | 单条真实路径跑通 | 跨平台、高并发长周期、高可用 |
  | 容器沙箱与云端持久化 | 该配置和特定压力场景 | 未纳入压测的极端场景 |
- 每条测试记录都要写 SHA、命令、环境、输出、跳过项和未验证项。旧的全量通过结果不自动适用于新提交。
- **递进验证**：快速轻量（相关单测、类型检查）→ 切片闭环 → 组合集成（MCP + 记忆 + 观测汇合后跑全链路 e2e，检查副作用和数据截断）。
- **集成分支与 main**：有依赖的 PR 按拓扑顺序分批合进临时集成分支；`main` 是“经过阶段性检验的稳定基线”，不等于全部能力达到最终交付标准（PR #149）。
- **合并前 Checklist**：head 与测试记录一致；Issue/Plan 待办逐项闭环；有覆盖默认入口、异常回退、断电恢复、权限拦截的真实日志；没混入 API Key、私人账号或构建产物；依赖第三方凭据或外部设备但未验证的，要如实批注。

## 3 reproduce：从零复现 0~9 步
**先做薄的纵向骨架**：用户输入 → 前端 → 后端路由 → Agent 调度与模型适配 → 可观测的回复。不要一开始就设计云基础设施、群聊、向量记忆和工具生态。每步都要有可观察的验证，并记录还没实现什么。

| 步 | 内容 | 完成标志 |
|-|-|-|

## 4 cases（案例，2 篇）

### 4.1 案例｜群聊演进从 #69 到 #78
完整走了一遍“体验反馈 → Web 调研 → Issue/Plan → 本地实现 → 源码复核纠偏 → 新一轮切片”。
1. **问题**：已有建群、`@Dot`、手动 Handoff，但链路是 `用户 @DotA → 授权 → A 返回 → 用户手动转交 @DotB`，不是在同一时间线上互读讨论。
2. **调研**：对比长期身份、每群独立会话、公开时间线、异步委派等模式，决定**复用现有 Agent Runtime、Durable 持久化和权限边界**，不引入第二套多智能体框架。
3. **Issue #69**：`Group × Dot` 持久会话 + 公开群时间线；后续 Dot 读已落库的正式发言；私人记忆和凭据不跨 Dot；受轮数上限、Token 预算和人工打断约束。PR #070 交付了时间线和按轮调度。
4. **新反馈**：仍像“接力作文”，于是立 Issue #71（增量上下文、自然接话、异步通信）。
5. **反转**：#070 其实已经支持互读，罪魁是旧 Prompt 的复述规训。#71 改为**协议解绑、增量上下文渲染、主动 Pass**，避免推倒重来。
6. **再拆分 #75–#78**（去噪且不做流式 / 默认策略、不静默覆盖 / 独立 Inbox / 有界并发、单 Session 单执行流）。把“不做什么”白纸黑字写进说明书。

### 4.2 案例｜MCP、电脑操作、记忆与观测并行开发
多个复杂提案并行时：识别公共依赖 → 避免重复建设 → 在审查中拦截组合问题。
1. **四份提案**：#103 MCP（工具目录、RPC、人工审批）、#101 浏览器/桌面操作（沙箱内截屏和键鼠模拟）、#110 每个 Dot 的 Mem0（托管记忆、偏好检索、私人数据隔离）、#111 Langfuse（Trace、Token、身份）。
2. **静态核查定依赖拓扑**：“直接复用”的设想太乐观，容器 Runner、Node 服务和云端持久化的工具注册机制并不通用。最后确定 #103 基础通道就绪后再做 #101；#110 独立推进；#111 与 #110 并行。
3. **分批切片**：先完成 MCP 目录和客户端、持久化审批和回执存储，再按依赖顺序合进集成分支；记忆和观测在独立分支自测。
4. **审查暴露的组合问题**：#116（区分“固定系统指令”和“低信任外部召回数据”，降权，并验证实际发给模型的 Payload 结构）；#115（两者单测各自全绿，组合后 Mem0 摘要改了请求头，Trace 身份丢失，要求补三方组合测试）。
5. **#149 阶段性基线同步**：如实写下尚未覆盖的物理真机极限场景。

#### 5.5.1 Issue #30：Bot-first 总路线图与 Goal Mode 交付契约
- 基线 `fe520f58`。目标是告别 Goal Prompt 幻觉，确立标准流水线和独立切片验收。
- **现状核对**：已有 Goal 调度原型、Scheduler、Durable Adapter 雏形，以及桌面外壳和会话入口。**断点**：真实任务走本地临时调度器、未接 Durable；没有跨端受控管道；没有统一的 Dot 实体和群聊上下文映射。
- **切片**：#31 Bot-first 首页和入口（只改路由和组件，不动持久执行协议）；#32 群聊对象模型（`Group`、`GroupTimeline`、`DotProfile`，同群不同 Dot 权限隔离）；#33 定向 Handoff（带状态，失败回滚到发起者）；#34 云端执行生命周期适配（桥接到 Durable Objects，断网、崩溃、重启后无损恢复）；#35 真实群聊交互与发布门禁（端到端自动化脚本通过才能合入）。
- **Non-Goals**：不接 MCP 和复杂浏览器自动化；不做跨组织向量知识库或长周期记忆挖掘；严禁用局部 mock 代替真实 ProductRuntime。

#### 5.5.2 Issue #61 / #64：对话优先与产品体系确立
- 基线 `d7c03a8`。把臃肿的“控制面板式”助手重构成以对话为核心的 Personal Agent。
- **痛点**：主屏塞满状态面板、资源监控和配置树，入口很深。
- **诉求**：打开就是对话；状态感知头像（有“呼吸感”）；以 Dot 为最小自治单元。
- **交付**：隐藏冗余监控；消息流支持 Markdown 高亮、代码一键复制、折叠式工具调用抽屉。#64：每个 Dot 有独立的 `Profile` / `Prompt` / `Workspace` / 工具权限，单聊和群聊里都能唤起。

#### 5.5.3 Issue #69：群级持久会话与多 Agent 讨论引擎（由 PR #70 推进）
- **痛点**：`用户 @DotA → A 返回 → 手动转交 @DotB → B 不知道 A 的上下文`。期望是代码审查、测试用例、架构设计等多个 Dot 在同一时间线上互读、持续讨论。
- **契约**：① 共享 `Group Timeline`，每个 Dot 保留独立的内部 Session，最终结论同步到公开时间线；② 后续 Dot 必须读到前序已落库的消息，私人记忆和凭据不能隐式穿透；③ 有界控制：Max Rounds、Token 预算阈值、用户随时 Stop，防止无限循环。

#### 5.5.4 Issue #71：对话协议纠偏与增量接话计划
- 背景：PR #70 合并后体验像“接力背诵”。直觉是链路坏了，复核发现 `Group × Dot` 机制完全正常，问题在 Prompt 强制“按序号总结上一位再表态”。
- **动作**：① Prompt Relaxation，改成“直接陈述增量观察、补遗漏或反驳”；② 上下文渲染优化，区分系统广播和成员消息，只注入**增量**时间线，防止撑爆窗口；③ 引入明确的 `reply` / `pass` 动作。

#### 5.5.5 Issue #75–#78：界面去噪、独立 Inbox 与有界多 Dot 并发
- 背景：界面里全是调度日志，多 Agent 并发有资源竞争风险。原则是克制，砍掉非核心功能。
- #75 去噪：隐藏调度日志、微小时间戳和调试 payload，只留重要异常、审批卡片和最终文本，**砍掉流式打字**；#76 修正一键开启策略的默认值，不静默破坏历史数据；#77 每个 Dot 一个基于消息队列的私有收件箱，支持异步交付和点对点信令；#78 受控并发锁，单个 Dot Session 严格单执行流，防止多协程状态污染。
- **为什么不做流式**：用户要的是高效 IM，不是终端日志滚屏；高频 WebSocket 中间态容易导致掉帧、重绘抖动和状态乱序。

#### 5.5.6 Issue #101–#111：前沿扩展集成
- 四个提案自上而下排列：#101 桌面控制（截屏、键鼠模拟、沙箱防护）→ #103 MCP（动态工具清单、RPC、人工审批弹窗）→ #110 Mem0（偏好挖掘、跨会话沉淀、检索增强）→ #111 Langfuse（Trace、Token 计费、多 Dot 监控）。
- **防护契约**：MCP 工具加载必须做 Schema 校验，高危操作（覆写本地文件、网络执行、终端命令）必须由用户在 UI 卡片上明确放行；记忆属于用户私有知识层，严禁作为未校验的 `system` 下发；Trace 上下文必须透传，记忆和摘要模块不能破坏 Trace ID 传播链。

#### 5.5.7 核心 PR 审查、排雷与基线集成档案
- **PR #002**：跨设备会话同步最小化接入。审查重点是复用 React/Electron 外壳、认证和工作区，不复制第二套运行时。

结构：任务（最终用户行为）→ 任务来源（Issue、PR/分支、历史基线 SHA，开始时重新检查最新状态）→ **先做**（读仓库规则、分支和未提交改动；分清已完成 / 只在其他分支 / 缺证据；列出切片、依赖、需保护的兼容行为和验收方式）→ **范围**（做 / 不做 / 复用与保护：身份、会话、权限、DB、API）→ **交付顺序**（最短可运行链路 → 错误、并发、恢复、撤权边界 → 用户入口与组合验证 → 文档和可审查 PR）→ **验收**（正常、故障、环境分别记录、回归）→ **工作方式**（基于证据、不重复实现；保留他人改动，不靠删测试或放宽权限来通过；遵守授权范围；环境阻塞时记录原因并继续其他工作，不把模拟说成真实验收；PR 里写 SHA、命令、结果、限制和未完成项）。

### 6.3 Issue 模板｜可交给开发 Agent 的任务
章节：背景与用户目标（谁、问题、期望的可观察行为、当前行为和复现）→ 基线与现有实现（时间、分支、核对的 SHA，实现前再确认 head；已有代码、测试、PR；待验证假设）→ 本次范围（可独立验证的勾选项）和**明确不做** → 依赖与兼容（前置 Issue/PR、可并行项、必须复用或不变的身份、存储、权限和 API、旧数据、旧客户端、运行中的任务）→ 建议实现顺序（核对现状 → 最小切片 → 后续切片 → 集成和文档；基线冲突时先拿出证据再调整）→ 验收与故障场景（正常路径、失败/权限/取消/重复、重启/重连/迁移、回归、环境真实性）→ PR 切片和回滚开关 → 完成说明（最终提交、命令、结果、未验证项、后续 Issue；**不用“应该可以”代替证据**）。不要在 Issue 里写真实凭据或私人数据。

### 6.4 PR 审查模板
审查对象（PR、时间与 head SHA、目标分支和基线、关联 Issue）→ 结论（可合入 / 需修复 / 信息不足，以及适用范围，比如“仅可进入集成分支”）→ 已核对（入口、权限兼容和数据、失败/重试/取消/重启、测试命令/环境/SHA）→ **每个问题五要素**：触发条件、实际与预期、影响和依据、修复要求（要维持的契约，不规定唯一实现）、验收 → 未验证项和后续（同步到 Issue）。

## 7 examples：最小对话骨架（7.1 及 4 个代码子页）

### 7.1 最小对话骨架（说明页）
- 链路：`index.html → POST /api/messages → mockReply() → JSON → 页面`，只用 Node.js 标准库，需要 Node 22+。
- 运行：`cd examples/01-minimal-chat && npm start`（或 `node server.mjs`），打开 http://127.0.0.1:3088；换端口用 `PORT=3089 npm start`；测试用 `npm test`（`node --test server.test.mjs`）。
- **动手练习**：改页面并发消息；改 `mockReply` 看服务端回复变化；空消息被拒、刷新后历史还在；重启服务后历史消失。下一步就是在 Issue 里定义持久化、会话身份和恢复要求。
- **边界**：是模拟回复，没有真实模型；只存在内存里，没有 DB、用户、Session 或权限；只监听 127.0.0.1，没有认证，不能暴露到公网。
- 页面末尾以附件卡片形式挂着 4 个源文件（index.html 2807B、package.json 318B、server.mjs 2552B、server.test.mjs 1302B），内容和下面 4 个子页一样。

### 7.1.1 index.html
单页聊天 UI：消息列表 `#messages`（aria-live）、表单 `#composer`、错误区 `#error`。`loadHistory()` 调 `GET /api/history` 渲染历史；提交时 `POST /api/messages`（JSON `{text}`），请求期间禁用按钮，成功后追加“我：…”和“模拟 Dot：…”，失败显示服务端返回的 error。

### 7.1.2 package.json
`personal-agent-minimal-chat`，`"type":"module"`，脚本 `start: node server.mjs`、`test: node --test server.test.mjs`，`engines.node >=22`，没有任何依赖。

### 7.1.3 server.mjs
- `mockReply(message)` 返回确定性的“模拟回复：我收到了“…””。
- `createApp()` 用 `node:http` 建服务，消息存在内存数组里：
  - `GET /` 返回 index.html；
  - `GET /api/history` 返回 `{messages}`；
  - `POST /api/messages`：流式读 body，**超过 4096 字节返回 413“消息过长”**；JSON 解析失败返回 400“请求格式不正确”；trim 后为空返回 400“请输入消息”；否则 push user 和 assistant 两条消息，返回 200 `{user, assistant}`；
  - 其他路径 404，异常 500“服务暂时不可用”。
- 直接运行时监听 `127.0.0.1:${PORT||3088}`。

### 7.1.4 server.test.mjs
用 `node:test` 和 `assert/strict` 写的一条集成测试：监听随机端口 → `GET /` 返回 200 且包含“最小对话骨架” → 发送空白消息得到 400，历史仍为空 → 发送“你好”得到 200，user.text 等于“你好”，assistant 角色正确、文本匹配“模拟回复” → 历史正好是这两条 → 测试结束时关闭服务。
