## 症状 → 原因 → 改动

### 移交项 3：D152 单闸是可确认草稿的唯一来源
- 症状（R17-01/02）：带员工括号的行，客户位用的是宽松口径；复合句保留了报单草稿；入口和循环各自判断拦不拦，口径不一致。
- 改动：
  - `confirmable-draft-gate.ts` 重写。`evaluateConfirmableReportDraft` 返回带品牌类型的 `ConfirmableDraftPass`，通行证只有本模块的 `issuePass` 能签发。
  - D146 未见否定补报、D147 污染行统一到 `textLevelImpurity`。入口（`employee-entry.ts`）和循环都调它，追问措辞用 `askForTextImpurity`，和原来逐字相同。
  - 括号非名字的判断统一到 `bracketImpurity`。
  - 删除 `compoundKeepsDraft` 开关。
  - 员工循环里组装报单草稿 payload 的地方只剩一处：`buildConfirmableReportDraft(pass, …)`。没有 pass 会直接抛错。二选一和「是新客户」的路径也先过闸；回「是」后会重新过一次闸。
  - 离线桩不声明 `liveModelAllowsDraft`，所以只有纯标准行能过闸。
  - 跨店和代报的拒绝措辞、拒绝语义都没动。
  - 闸内客户位补了一条规则：客户名里有空白或【】[] 时不放行。这样表外前缀的残留不会被当成客户名出草稿。
- 结构测试 `tests/r18/r18-single-gate-structure.test.ts` 钉住三件事：payload 组装只有一处；每个调用都拿闸给的 pass；入口和循环从不声明模型放行。

任何复合句都整句先问，包括后半句是改账、预约或宣传的。锁定集里因此掉下来的条目标为 `pending_formal_test`，见下文。

### D158 行首前缀
- 新增 `config/line-prefix-fixed.json`（版本 D158-r18，frozen）：
  - 标签：报单、报个单、报一下、报业绩、今日报单、开单、报惮。前面可以有【】，后面要跟冒号或空白。
  - 寒暄：老板好、店长好、大家好、早、早上好、晚上好，再加 D135 客套语（读 remark-courtesy.json）。整段都是寒暄、后面跟标点或空白时才剥。
- `standard-line.ts` 的 `LINE_PREFIX` 只保留序号、项目符号和圈号。剥前缀的顺序是先寒暄、再标签、再序号。
- R17 曾经会剥的「报数 / 报个数 / 今日报数 / 今天报数」和任意【…】现在都在表外，一律先问。
- 吐槽、情绪类开头不在表里，仍然先问。r3a 那条测试保持「先问」。
- **相关评测条目已恢复**（「报惮」在表里）。
- 反例测试覆盖：表外标签、表外【…】、情绪开头先问；客户名开头的行不被误剥。

### D159 括号里写店长
- 括号是「姓＋店长」时，在本店在职店长里按姓找：唯一对上就记给他；对不上或对上多个就先问；他店店长不算。
- 「老板」在粗筛表里，先问。
- 这一步放在跨店检查之前，否则会被拆成「X店」＋「长」，走到跨店拒绝（这是本轮修掉的一个 bug）。
- 跨店和代报的拒绝语义不变。

### D160 重复回「对」
- 只回 `Front Claw：这笔已经入账了，不用重复确认。`，不多记一笔。
- 并发时，没抢到状态的一方（transitionPending 失败、草稿已是 confirmed 或 confirming）回这句。
- 顺序重复：报单确认入账后记一个本人本会话的标记；紧接着再回「对」或「全部确认」，就回这句。循环里任何其他消息都会清掉这个标记。
- PG 并发测试的输家断言收紧为：输家回复**严格等于**这句，且不含「已入账」；两条回复里恰好一条含「已入账」。r2-pg 的顺序重复确认也改成严格等于这句。
