## 1. 改动（相对 M03 树）

  - 新增 `commitConfirmingTarget` 和 `commitConfirmingCorrection`，PG 和内存两套实现。
  - 事务顺序：策略行 FOR SHARE（guard）→ 草稿 confirming→confirmed 条件更新 → 账目行按 entryId 排序 FOR UPDATE，比对版本 → 改账 + revision（确定性 ID，ON CONFLICT DO NOTHING）+ 改账通知 pending 行。

  - 不改 schema。

## 3. 过程中发现并修掉的

- **“刚才那笔”选错条**：固定时钟下，多批或多笔时间戳相同，PG 并发测试里出现“expected 2 to be 1”。改为并列即拒绝（AMBIGUOUS_RECENT），测试改用走动时钟，并补了单元测试。
- **M9 目标 guard 漏测**：补了“目标提交事务内撤权”测试。
- **内存实现未覆盖**：补了 MemoryPerformanceStore 同语义测试。
- **先读账本再鉴权**：报数和更正路径都改为先查能力，测试断言无能力者零账本读取。
- **目标对象离职或调店后仍能确认**：确认时加了在职/门店检查和测试。
- **PG 测试偶发**：
  - 撤权竞态的“拒绝 > 0”偶尔不满足：改为交替错开起跑。
  - 重放测试第 126 行偶发失败：原因是 M02 请求预算按 messageId 做进程内去重，输掉竞争的进程再收到同一消息时，原样回“草稿版本已变化，请查原操作结果”。账目本身正确，所以改的是断言（见 §5 第 4 条）。
- **调参语料被 json.dump 重排**：用 git checkout 还原后，改为按文本追加。

## 5. 已知限制

1. 确认时的重复复查在提交事务之外，存在一个小竞态窗口（极端情况下，两份内容相同的草稿几乎同时确认，可能都入账）。要彻底关掉，需要把去重放进事务，或加唯一约束（涉及 schema，留待拍板）。
2. 旧（非 employeeLoop）入口仍保留直接 setTarget/reviseEntry 路径。在 employeeLoop 模式下不可达（有测试锁定），但旧模式下这条路径不走 M04 的回显、锁和版本校验。
3. 目标没有单独的修订表：审计依赖已确认的目标草稿（含原值和新值）加上 updated_by/updated_at。
4. 同一进程收到同一 messageId 的重发，原样回第一次的回复（M02 语义）。如果第一次输掉了并发，用户看到的是“草稿版本已变化，请查原操作结果”，要发「入账结果」才能看到已改账。
5. 改账通知只落 pending 行，不派发（M06）。
6. PG17 不是线上版本；没有声称达到任何延迟目标。
