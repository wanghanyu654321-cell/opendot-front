## 1. 背景与用户目标

诉求 ③④⑦。员工、店长、老板能做什么、看哪些店由服务端决定，撤权立刻生效；拒绝时读、写、通知都不越权。
可复现的现状缺口（M02 head）：
- `assistant-tools.ts`：老板的门店范围 = `distinctStores(全部人员)`，即“未显式列出 = 全部门店”；店长/老板能力只按 `Person.tier` 判断，没有门店集合、状态、策略版本。
- `employee-loop.ts`（M01/M02 窄入口）只有本人/同店代报和受控名单开关；没有店长/老板查询，也没有执行与提交时的统一鉴权、撤权顺序。
- 旧入口 `front-claw-boot.ts` 非 employeeLoop 模式 `remember()` 会用 SDK 岗位角色（含 manager）**改写** people 表的正式 tier——这是本仓库中“临时名单/角色覆盖正式授权”的实际路径。F 的 `ownerAccountIds` 覆盖不在本仓库（未合入），不复制。
首批试用：B 店；测试员工A测试账号按老板→店长→员工逐级降权，**仅在合成数据中验证，不写真实配置**。

## 3. 范围

- [ ] 策略 = PG config 键 `front-claw-access`（JSON，无 schema 变更）：`version`（单调递增）、企业层、门店层、角色层、成员授权（角色、门店集合、状态、可选能力收窄）、可选平台层（OpenDot，M07 前不传）。
- [ ] 有效能力 = 已实现 ∩ 企业 ∩ 门店 ∩ 角色 ∩ 成员（若列出）∩ 平台（若传入）。显式空列表=空；缺层=拒绝；坏 JSON/未知能力/类型不符=整份策略视为损坏 → 拒绝所有敏感读写。
- [ ] 角色只来自策略成员授权且必须与 people.tier 一致；不从聊天正文、岗位角色或临时名单推导。老板门店集合必须显式非空；员工/店长门店集合只能是本人所在店。
- [ ] 鉴权点：入口（解析身份后）、执行（业务读写前）、草稿创建前、草稿确认（转换前）、事务提交（同一事务内 `FOR SHARE` 读策略行）、查询发送前（回复生成后再验）。
- [ ] 撤权：`updateAccessPolicy` 在事务内 `FOR UPDATE` 读旧策略、校验 expectedVersion 与版本递增、写新策略和审计记录；与提交共享同一行锁 → 先后确定。旧版本配置回写被拒，不能复活已撤权身份。
- [ ] 新能力：`progress_other`、`store_summary`、`unreported`、`stores_ranking`；查询按授权门店下推到 `listEntries({storeId})`。
- [ ] 营销（M02）在策略模式下还需 `marketing` 能力；B 店首批不开。
- [ ] 策略模式下 `remember()` 不写 people（已是 employeeLoop 行为），并加测试锁定；不再存在由岗位角色改写 tier 的路径。
- [ ] 矩阵与负例测试（MemorySql）+ PG17 集成：降权后旧确认被拒（含已入队后降权的竞态）、撤权与提交并发顺序。

## 5. 依赖与兼容

依赖 M01、M02。保留 person/account/entry/draft ID 与 M01 受控开关 `employee-loop:m01`（策略模式下两者都要满足才可写）。未启用策略模式时保持 M01/M02 行为（只本人/同店代报，无管理查询），不扩大权限。旧会话、旧草稿不保留旧授权：确认时按当前策略重判。SQLite grant 不作业务权威。

## 6. 验收与故障

- 矩阵：A 店员工、A 店店长、B 店店长、只授权 A 店的老板 × {本人报数、同店代报、本人进度、他人进度（同店/他店）、门店汇总（本店/他店）、谁没报、门店排名}。
- 负例：查他人、查他店、伪造老板（tier/策略不一致、正文自称）、空配置、坏配置、旧缓存（策略变更后立即生效）、旧草稿（降权后确认）、入队后降权；拒绝时 entries/drafts 不变、PG 读不越门店、send 未调用。
- PG17：降权后旧确认被拒；确认已进入执行后才降权被拒；撤权与提交并发，两种先后都给出一致结果与事务顺序证据。
- 回归：M01、M02 专项，相关回归，全量 vitest（已知 live-model-smoke 2 失败），test:pg，tsc，build。

## 7. 开关与回滚

`accessPolicy: true`（handler/boot/pilot 选项）启用策略模式；开启后策略缺失或损坏一律拒绝。关闭即回到 M02 行为（不扩大权限）。回滚 = 不应用 m03.patch。
