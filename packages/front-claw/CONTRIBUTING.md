# 贡献与开发规范

## 分支

- `main` 是受保护分支，只通过 PR 合并，不直接推送。
- 功能分支：`feat/<主题>`；修复：`fix/<主题>`；文档：`docs/<主题>`；修复轮：`fix/r<轮次>-<主题>`（例如 `fix/r18-c015-prefix`）。
- 一个分支只做一件事，合并前先 rebase 到最新的 `main`。

## 提交信息

采用 Conventional Commits，主题用英文祈使句，正文可用中文：

```
<type>(<scope>): <summary>

<为什么改、改了什么、怎么验证>
Refs: #<issue>
```

`type`：`feat` `fix` `docs` `test` `refactor` `chore` `ci`。`scope` 示例：`report` `gate` `ledger` `opendot` `migration` `notify`。

## PR

- 使用 `.github/pull_request_template.md`，写清动机、改动、验证结果和风险。
- 必须通过 CI（typecheck、build、单元测试）。
- 涉及 `migrations/` 的 PR 必须同时提供 down 脚本，并在合成库上跑通 `npm run test:pg`。
- 改了产品口径的，要在 PR 里写明对应的 D 号，并在 `docs/product/decisions/` 追加记录（**只追加，不改旧条目**）。

## 审查规则

- 至少一名审查人批准后才能合并。开发者不审自己的准入。
- 门禁评测用**独立留出集**，由审查方编写、保管。开发侧不读留出集、映射和复审原文，也不把它们提交进仓库。
- 准入线：门①（格式清楚的报单直接出草稿）≥ 95%；门②（该问的不执行）= 0；门③、门④在正式实测里判。
- 新行为先写会失败的测试，再做最小实现。关键防线要有变异测试（故意改坏后测试必须失败）。
- 不在报告里把合成环境的结果写成线上已验证。

## 安全

- 不提交任何 `.env`、密钥、token、密码、私钥、cookie、连接串里的密码，也不提交真实员工、客户数据。
- 测试数据只能用虚构人名。服务器地址、企微 ID、线上库名用占位符。
- 提交前本地跑一次秘密扫描（例如 `gitleaks detect --no-git -s .`）。
- 停服务、删数据、动线上库、开真实测试窗口，都需要项目负责人本人书面批准，先把具体命令列出来过目。
